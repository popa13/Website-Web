Le pipeline de mathopo.ca

Comment mon site est écrit, construit, hébergé et mis à jour, puis comment refaire exactement la même chose chez toi.

site=N∘G∘B(contenu)

où
B
build.py transforme les pages Markdown en HTML ;
G
git push envoie le projet sur GitHub ;
N
Netlify relance build.py sur ses serveurs et publie le résultat.

Le carré commute : Netlify exécute le même build.py que toi, donc le site en ligne est exactement celui que tu vois sur ton ordinateur avant de pousser.

Aucun cadriciel à apprendre : un script Python qu’on peut lire en entier, des pages en Markdown (avec du HTML quand on en a besoin), MathJax pour les formules, deux langues, et un hébergement gratuit qui se met à jour tout seul à chaque git push.

Commencer les étapes

Comment mon site fonctionne

Mon site est un site statique : des fichiers HTML, CSS et JavaScript servis tels quels, sans base de données ni serveur à entretenir. Tout le travail se fait avant la mise en ligne, par un script Python qui assemble les pages. Le pipeline actuel date de janvier 2026 ; depuis, chaque modification du site est un commit.

Anatomie du dépôt

Voici la structure de base, sans le détail de mes pages. Clique sur un élément pour voir son rôle.

En noir, ce que tu écris toi-même. En bleu italique, ce que build.py produit ou copie : on n’y touche jamais à la main.

mon-site/

Le dépôt Git. Tout le projet y vit : les sources, le script et le site final. GitHub en garde l’historique complet, ce qui permet de revenir à n’importe quelle version du site.

build.py

Le moteur. Il lit chaque page Markdown, remplace les jetons par des données, convertit le tout en HTML, l’insère dans le gabarit et écrit le résultat dans public/. Tu le lances avec python3 build.py, et Netlify lance exactement la même commande.

netlify.toml

La configuration de Netlify : la commande à exécuter (python3 build.py) et le dossier à publier (public). Aucun réglage de build à faire dans l’interface de Netlify.

requirements.txt

Les trois bibliothèques dont build.py a besoin : Markdown, Jinja2 et PyYAML. Netlify les installe tout seul avant chaque build.

.gitignore

Ce que Git doit ignorer : l’environnement Python local, et les copies d’applications que build.py refait de toute façon à chaque build. Ça évite de stocker deux fois les gros fichiers dans l’historique.

templates/base.html

Le gabarit commun à toutes les pages : en-tête, menu, bouton de langue, MathJax et pied de page. Chaque page y est insérée à l’endroit de {{ content }}. Une modification ici change tout le site d’un coup.

content/

Tout ce que tu écris : les pages, rangées par langue, plus les données et les scripts qu’elles utilisent.

content/fr/

Une page = un fichier .md. Il commence par un petit en-tête YAML (titre, onglet du menu, largeur), suivi du contenu en Markdown ou en HTML. recherche.md devient recherche.html.

content/en/

Les mêmes pages en anglais, avec les mêmes noms de fichiers. C’est ce qui permet au bouton FR/EN de passer d’une version à l’autre de la même page.

content/data/

Les données structurées en YAML : séminaires, publications, listes. Chaque champ peut être bilingue ({fr: …, en: …}). Une page y fait référence par une simple ligne-jeton, que build.py remplace par du HTML.

content/js/

Les scripts JavaScript utilisés par les pages (un explorateur de fractales, par exemple). Ils sont copiés dans public/ à chaque build.

apps/une-app/

Une application interactive autonome, dans son propre dossier : du HTML, du CSS et du JavaScript, sans étape de compilation. Elle fonctionne seule ; build.py la copie dans public/apps/ et une page l’affiche dans un cadre.

public/

Le site final, tel que Netlify le sert. Attention : c’est un dossier mixte. Il contient les pages générées, mais aussi des fichiers déposés à la main (images, PDF, feuille de style). Il est donc versionné dans Git, et il ne faut jamais le vider.

public/*.html, public/en/

Les pages produites par build.py : la première langue à la racine, les autres dans un sous-dossier. On ne les modifie jamais à la main, puisqu’elles sont réécrites à chaque build.

public/apps/

Les copies des applications. Elles figurent dans .gitignore, car Netlify les refait à partir de apps/.

public/images/, public/documents/

Les images et les PDF (articles, affiches, présentations), déposés à la main. Une page y renvoie par un lien ordinaire.

public/style.css

La feuille de style, écrite à la main. Le gabarit y fait référence ; build.py n’y touche pas.

Ce que fait build.py, dans l’ordre

  1. Il copie les scripts partagés de content/js/ dans public/.
  2. Il copie chaque application de apps/ dans public/apps/.
  3. Pour chaque langue, puis pour chaque fichier .md, il :
    1. sépare l’en-tête YAML (titre, onglet actif, largeur) du contenu ;
    2. remplace les jetons, comme <!-- LISTE:publications -->, par du HTML construit à partir d’un fichier YAML ;
    3. convertit le Markdown en HTML ;
    4. insère le résultat dans le gabarit, avec les bons liens de menu et de langue ;
    5. écrit public/page.html, ou public/en/page.html pour la deuxième langue.

Ce qui rend mon site un peu particulier

  • Bilingue sans effort. Chez moi, l’anglais est à la racine et le français dans /fr/ (et une page existe aussi en mandarin). Chaque page a le même nom de fichier dans toutes les langues, et le gabarit calcule le lien vers l’autre version.
  • Des pages alimentées par des données. Ma page de séminaires contient un peu de texte et une ligne-jeton par session. build.py la remplace par un tableau dépliable construit à partir d’un fichier YAML (date, conférencier, résumé dans les deux langues, vidéo YouTube intégrée). Ajouter un séminaire, c’est ajouter une dizaine de lignes de YAML.
  • Des applications interactives à part. Chaque application (preuves à compléter, cartes, jeux, visualisations pour mes cours) vit dans son propre dossier sous apps/, en HTML, CSS et JavaScript pur. build.py la copie dans public/apps/, et une page l’affiche dans un <iframe> avec ?lang=fr ou ?lang=en, ou y renvoie par un lien.
  • Un dossier public/ mixte. Il contient les pages générées, mais aussi les images, les PDF de mes articles et présentations, et les anciens sites de cours. Il est versionné dans Git ; seules les copies d’applications sont ignorées.
  • De petits scripts d’appoint. Pour ce qui change souvent (des données publiques téléchargées d’une API, une nouvelle version d’un jeu), un script récupère la nouveauté et la range au bon endroit. L’un d’eux relance même build.py et, avec l’option --push, fait le commit et le push. Netlify s’occupe du reste.
  • L’allure LaTeX. MathJax 3 pour les formules et la police Computer Modern pour le texte : le site a l’air d’un document LaTeX.

La boucle de tous les jours

  1. Je modifie une page dans content/fr/ ou content/en/, ou un fichier de données.
  2. Je lance python3 build.py, qui réécrit public/.
  3. Je vérifie le résultat dans le navigateur, avec un petit serveur local.
  4. Je fais git add puis git commit avec un message qui décrit le changement.
  5. Je fais git push. Netlify reçoit le signal de GitHub, relance build.py et publie le site en une ou deux minutes.

À ton tour, étape par étape

Prévois une heure ou deux pour la première mise en ligne. Les commandes sont écrites pour macOS et Linux. Sous Windows, remplace python3 par py, et active l’environnement Python comme indiqué à l’étape 3.

1

Installe les outils

  • Python 3.9 ou plus récent : vérifie avec python3 --version.
  • Git : vérifie avec git --version.
  • Un compte GitHub et un compte Netlify. Crée ton compte Netlify avec ton compte GitHub : l’étape 9 en sera plus simple.
  • Un éditeur de texte qui comprend Markdown et Python (VS Code, par exemple).
2

Récupère le squelette

Le kit de départ contient la structure complète, prête à compiler : le moteur, le gabarit, deux pages bilingues, une liste alimentée par un fichier YAML et une petite application (l’ensemble de Mandelbrot, évidemment). C’est une version épurée de mon propre dépôt.

Décompresse-le où tu veux. Tu obtiens un dossier mon-site/ organisé comme l’anatomie plus haut.

Un environnement virtuel garde les bibliothèques du site séparées du reste de ton ordinateur.

Le fichier requirements.txt est le même que le mien. Netlify le lira aussi, à l’étape 9 :

4

Le gabarit : templates/base.html

Toutes les pages partagent ce squelette. Les parties en bleu sont des variables Jinja2 que build.py remplit : le titre, le menu, les liens de langue et, surtout, {{ content | safe }}, où vient se placer le contenu de la page.

Les chemins commencent par / (/style.css) : ils fonctionnent dans tous les sous-dossiers de langue. Sur mon site, ils sont relatifs (../style.css dans /fr/) ; la version absolue t’évite de gérer les ../.

5

Le moteur : build.py

168 lignes, à lire une fois en entier. Pour l’adapter, tu n’as qu’à modifier le haut du fichier : SITE et AUTEUR, la liste LANGS (la première langue va à la racine), le MENU, et STANDALONE_DIRS quand tu ajoutes une application.

Mon propre build.py a la même structure et les mêmes conventions (clés page_title, nav, wide dans l’en-tête des pages). Il est plus long seulement parce qu’il gère plusieurs types de jetons pour les séminaires.

9

Branche Netlify

Tout ce dont Netlify a besoin tient dans ce fichier, déjà à la racine du kit :

  1. Dans Netlify, ajoute un nouveau projet en l’important depuis Git, choisis GitHub, puis ton dépôt.
  2. Netlify lit netlify.toml : la commande de build et le dossier à publier sont déjà remplis. Il installe aussi tout seul ce qui figure dans requirements.txt.
  3. Lance le premier déploiement. Ton site reçoit une adresse du type nom-au-hasard.netlify.app, que tu peux renommer dans les réglages du projet.
  4. Sur les comptes récents, un nouveau projet peut être privé par défaut : publie-le depuis le tableau de bord si l’adresse ne s’ouvre pas.

À partir de là, chaque git push sur main reconstruit et republie le site. Si un build échoue, le journal de déploiement de Netlify montre la sortie de build.py, ligne par ligne, et l’ancienne version reste en ligne.

10

Branche ton nom de domaine (facultatif)

Achète un domaine chez un registraire, puis ajoute-le dans la section des domaines de ton projet Netlify. Deux choix : confier la gestion DNS à Netlify (tu remplaces les serveurs de noms chez ton registraire), ou ajouter chez ton registraire les enregistrements que Netlify t’indique. Le certificat HTTPS est ensuite créé et renouvelé automatiquement, sans frais, même avec l’offre gratuite.

Aller plus loin

Un nouveau type de jeton
Copie le trio LISTE_RE, rendre_liste, injecter_jetons : une expression régulière qui repère le commentaire, une fonction qui lit le YAML et produit du HTML, une ligne de plus dans injecter_jetons. C’est exactement ainsi que sont faits mes tableaux de séminaires.
Une application interactive
Crée apps/mon-app/index.html, ajoute ("apps/mon-app", "apps/mon-app") à STANDALONE_DIRS, puis affiche-la dans une page avec un <iframe src="/apps/mon-app/index.html?lang=fr">. L’application lit lang dans son adresse pour choisir sa langue.
Une troisième langue
Ajoute son code à LANGS, crée content/zh/ (par exemple) et ajoute la traduction de chaque titre dans MENU. Une page absente dans cette langue renvoie simplement vers son accueil.
Un script d’appoint
Pour des données qui changent souvent : un script récupère la nouveauté, l’écrit dans content/data/ ou apps/, lance python3 build.py, puis git commit et git push si on lui passe --push.

Pièges à éviter

Les maths et Markdown ne s’entendent pas toujours
En Markdown pur, \( perd son antislash, \\ devient \ et deux * deviennent de l’italique. Écris les formules courtes avec $…$, et place les autres dans un bloc HTML (<div>, <p>) : Markdown ne touche pas à l’intérieur. C’est ce que je fais sur toutes mes pages.
Ne vide jamais public/
Tes images, tes PDF et ta feuille de style y vivent. build.py écrase les pages qu’il produit, sans rien supprimer d’autre. Pour retirer une page, efface son .md et son .html.
Le même nom de fichier dans chaque langue
content/fr/cours.md et content/en/cours.md, pas courses.md d’un côté : sinon le bouton de langue renvoie vers l’accueil.
Chaque push en production coûte des crédits
Sur les comptes Netlify gratuits créés depuis septembre 2025, le mois compte 300 crédits, et chaque déploiement en production en coûte 15 : une vingtaine de mises en ligne par mois, moins si le site consomme de la bande passante. Fais autant de commits que tu veux, mais vérifie en local et pousse par lots. Les déploiements de prévisualisation (branches, demandes de fusion) ne coûtent rien.
La version de Python sur Netlify
Si le build fonctionne chez toi mais échoue sur Netlify, fixe la version de Python dans netlify.toml en décommentant la section [build.environment].
Les gros fichiers
Git garde tout pour toujours. Ne versionne pas deux fois la même chose (les copies dans public/apps/ sont ignorées pour cette raison) et évite les vidéos : YouTube s’en charge mieux.
